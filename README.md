# Mini NPU Simulator

사람은 눈으로 보면 무엇이 '십자가(+)'이고 무엇이 '엑스(X)'인지 바로 알 수 있지만, 컴퓨터는 그림을 보지 못하고 **숫자만** 읽을 수 있습니다.  
이 프로그램은 그림을 **숫자 빙고판(2차원 배열)**으로 바꾼 뒤, 컴퓨터가 어떻게 십자가와 X를 구별하는지 직접 계산해 보고 속도까지 측정해 보는 **Mini NPU 시뮬레이터**입니다.

---

## 1. 실행 방법

1. **준비물**: Python 3.8 이상 (본 환경: Python 3.12)
   - 외부 라이브러리(NumPy, pandas 등)는 전혀 쓰지 않고, 파이썬에 기본으로 들어있는 표준 라이브러리(`json`, `time`)만 사용했습니다.
2. **파일 위치**: `main.py` 파일과 `data.json` 파일을 **같은 폴더(`mini_npu`)** 안에 넣어둡니다.
3. **실행 명령어**: 터미널(명령 프롬프트)을 열고 `python main.py` 를 입력한 뒤 엔터를 칩니다.
4. **모드 선택**: 화면에 메뉴가 나오면 원하는 숫자를 입력합니다.
   - `1`: **사용자 입력 모드 (3×3)** — 키보드로 3×3 숫자 빙고판(필터 A, 필터 B, 패턴)을 한 줄에 숫자 3개씩 공백으로 구분해 입력하고 결과를 확인합니다.
   - `2`: **data.json 분석 모드** — `data.json` 파일에 들어 있는 5×5, 13×13, 25×25 크기 문제들을 한꺼번에 채점하고 속도 표와 결과 요약을 확인합니다.
   - `0`: **종료** — 프로그램을 끝냅니다.

---

## 2. 구현 요약 (어떻게 만들었나요?)

### ① MAC 연산 (같은 칸끼리 곱해서 다 더하기)
- **MAC**은 **Multiply(곱하고) + Accumulate(쌓아서 더한다)**의 줄임말입니다.
- 입력 그림(패턴) 빙고판과 기준(필터) 빙고판을 똑같이 겹쳐 놓고, **같은 자리에 있는 숫자끼리 곱한 뒤 그 결과를 저금통에 전부 더하는 방식**입니다.
- 점수가 높을수록 "이 그림은 이 필터 모양과 더 비슷하다!"라고 판단합니다.
- 외부 라이브러리 없이 파이썬의 `for` 반복문 두 개(줄 내려가기 + 칸 이동하기)로 직접 구현했습니다.

### ② 라벨 정규화 (이름 통일하는 번역기)
- `data.json` 파일을 열어보면 같은 십자가 모양인데 필터에는 `"cross"`, 패턴 정답(`expected`)에는 `"+"`라고 제각각 적혀 있습니다.
- 컴퓨터는 `"cross"`와 `"+"`를 완전히 다른 글자로 취급하기 때문에, 비교하기 전에 무조건 **`"Cross"`**와 **`"X"`** 두 가지 표준 이름으로 통일해 주는 번역기 함수(`normalize_label`)를 만들었습니다.

### ③ 동점 처리 정책 (`epsilon = 1e-9`)
- 컴퓨터는 0과 1로 소수점을 저장하기 때문에 계산할 때 아주 미세한 오차를 냅니다. 예를 들어 사람 눈에는 `0.1`을 9번 더하면 `0.9`지만, 컴퓨터는 `0.8999999999999999`로 계산합니다.
- 이 작은 오차 때문에 사실상 동점인데 한쪽이 이겼다고 착각하는 것을 막기 위해, **두 점수의 차이가 `0.000000001`(`1e-9`)보다 작으면 동점(`UNDECIDED`)**으로 처리합니다.

### ④ 오류 방지 (프로그램이 멈추지 않게 하기)
- **모드 1**: 사용자가 한 줄에 숫자를 3개가 아닌 2개만 치거나, 글자(`a b c`)를 잘못 입력하면 오류 안내 문구를 출력하고 다시 입력하도록 유도합니다.
- **모드 2**: `data.json` 안에 행렬 크기가 안 맞거나 잘못된 데이터가 섞여 있어도 프로그램이 비정상 종료되지 않고, 해당 케이스만 `FAIL`로 기록한 뒤 다음 케이스로 넘어갑니다.

## 3. 결과 리포트

### 3-1. FAIL(실패) 케이스 원인 분석
`data.json`의 총 6개 테스트를 실행한 결과 **3개 PASS(통과), 3개 FAIL(실패)**이 나왔습니다.

1. **`size_5_1` (FAIL - 동점 규칙)**
   - 원래 정답은 `X`지만, Cross 점수(`0.9000000000000000`)와 X 점수(`0.8999999999999999`)의 차이가 `1e-9`보다 작아서 `UNDECIDED`(판정 불가)가 되었습니다.
2. **`size_13_2` (FAIL - 동점 규칙)**
   - 원래 정답은 `Cross`지만, Cross 점수(`7.4999999999999973`)와 X 점수(`7.5000000000000000`)의 차이가 `1e-9`보다 작아서 `UNDECIDED`가 되었습니다.
3. **`size_25_1` (FAIL - 동점 규칙)**
   - 원래 정답은 `X`지만, Cross 점수(`4.9000000000000004`)와 X 점수(`4.8999999999999986`)의 차이가 `1e-9`보다 작아서 `UNDECIDED`가 되었습니다.

- **왜 실패가 났을까요? (원인 진단)**
  - 이 3개의 실패는 코드가 잘못 짜였거나(로직 오류) 파일 형식이 깨진 것(스키마 오류)이 아닙니다. **필터의 가중치 설계와 컴퓨터의 부동소수점(소수점) 계산 오차** 때문에 두 점수가 사실상 똑같이 나온 **수치 비교 문제**입니다.
  - 만약 `epsilon(1e-9)` 규칙 없이 단순히 "큰 숫자가 이긴다(`>`)"로만 비교했다면, `size_5_1`은 정답이 `X`인데도 미세한 오차(`0.9 > 0.8999999999999999`) 때문에 엉뚱하게 `Cross`라고 틀린 답을 냈을 것입니다.
  - 허용오차(`1e-9`) 기반 비교 정책을 적용한 덕분에, 오차 범위 안에서 점수가 겹치는 경계 문제들을 억지로 찍지 않고 안전하게 `UNDECIDED`로 걸러낼 수 있었습니다.

### 3-2. 성능 분석 및 시간 복잡도 ($O(N^2)$)
화면에 글자를 출력하거나 파일을 읽는 시간(I/O)은 제외하고, **순수하게 MAC 연산 함수만 호출하는 구간**을 스톱워치(`time.perf_counter`)로 10번씩 반복 측정해 평균을 낸 결과입니다.

| 빙고판 크기 ($N \times N$) | 평균 걸린 시간 (ms, 10회) | 총 계산 횟수 ($N^2$) |
| :---: | :---: | :---: |
| 3×3 | 0.0013 | 9번 |
| 5×5 | 0.0022 | 25번 |
| 13×13 | 0.0110 | 169번 |
| 25×25 | 0.0360 | 625번 |

### 3-2. 성능 분석 및 시간 복잡도 (O(N²))
화면에 글자를 출력하거나 파일을 읽는 시간(I/O)은 제외하고, **순수하게 MAC 연산 함수만 호출하는 구간**을 스톱워치(`time.perf_counter`)로 10번씩 반복 측정해 평균을 낸 결과입니다.

| 빙고판 크기 (N×N) | 평균 걸린 시간 (ms, 10회) | 총 계산 횟수 (N²) |
| :---: | :---: | :---: |
| 3×3 | 0.0013 | 9번 |
| 5×5 | 0.0022 | 25번 |
| 13×13 | 0.0110 | 169번 |
| 25×25 | 0.0360 | 625번 |

- **시간 복잡도가 O(N²)인 이유**
  - 가로가 N칸, 세로가 N칸인 빙고판의 모든 칸을 한 번씩 계산하려면 이중 `for` 반복문이 총 **N × N = N²번** 돌아야 합니다.
  - 예를 들어 5×5는 25번만 계산하면 되지만, 가로·세로가 5배 커진 25×25는 계산 횟수가 5배가 아니라 **5 × 5 = 25배(625번)**로 확 늘어납니다.
- **측정 결과 해석**
  - 실제로 측정된 평균 시간도 5×5(`0.0022 ms`) → 13×13(`0.0110 ms`) → 25×25(`0.0360 ms`)로, 크기가 커질수록 걸리는 시간이 계산 횟수(N²)에 비례해서 빠르게 늘어나는 **O(N²)** 특성을 그대로 확인할 수 있었습니다.
  - 이처럼 이미지 크기가 커질수록 계산량이 제곱으로 폭발하기 때문에, 실제 AI에서는 수천 개의 MAC 연산을 한꺼번에 동시 처리(병렬 처리)하는 전용 칩(**NPU**)이 필요하다는 것을 알 수 있습니다.
